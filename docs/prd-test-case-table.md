# PRD: Searchable Test-Case Table

## Summary

Add a test-case table to the interactive HTML report generated by
`playwright-timeline-reporter`. The table will list every recorded Playwright test execution and
allow users to search by test name and sort by name or total execution time. Its purpose is to make
failed and slow tests easy to find without changing the consumer's Playwright configuration or the
reporter's input/output data contract.

## Problem

The timeline chart is well suited to understanding parallel execution, but it is not an efficient
way to scan a large run for a particular test or rank tests by duration. Users need a tabular view
of the same test data so they can quickly locate a known test, inspect failures, and identify the
longest-running tests.

## Goals

- Display every `TestTimings` entry already present in the embedded `#timeline-data` JSON.
- Provide a text search that filters rows by test name.
- Sort rows by test name and total duration in ascending or descending order.
- Clearly expose test outcome and duration, making failed and slow executions easy to identify.
- Work for normal reports, multi-project reports, sharded/merged reports, and reports containing
  retries.
- Preserve the existing reporter configuration, Playwright setup, and generated JSON schema.

## Non-goals

- Changing the Node-side reporter collection pipeline or adding fields to `TestTimings`.
- Replacing the existing command-palette search or altering timeline-chart filtering/focus behavior.
- Adding server-side search, pagination, virtualisation, export, saved filters, or persistent table
  preferences in the first release.
- Aggregating retries into a single logical test row. Each recorded test execution remains visible.

## Users and Scenarios

1. As a test engineer, I can view a row for every recorded test execution in the generated report.
2. As a test engineer, I can search for all tests whose name contains a phrase, regardless of case.
3. As a test engineer, I can sort test names alphabetically in either direction.
4. As a test engineer, I can sort total duration longest-first to find performance bottlenecks, or
   shortest-first for comparison.
5. As a test engineer, I can see a test's status in the table and quickly recognize failures while
   reviewing the duration-ordered list.
6. As a test engineer using projects, shards, or retries, I can distinguish executions using the
   existing project/shard and retry information where it is available.
7. As an existing package consumer, I can update the package and receive the table in my generated
   report without modifying my Playwright reporter configuration, tests, CI pipeline, or JSON data.

## Functional Requirements

### Data compatibility

- Build the table solely from the existing browser-side `TestTimings[]` read from `#timeline-data`.
- Do not change the serialized report format, reporter options, report generation process, or
  required Playwright metadata.
- Support all valid values already emitted for `status`, `retry`, `projectName`, and optional
  `mergeReportId`.
- A retry is a separate execution and must have its own row. Do not silently deduplicate rows by
  `testId`.

### Table content

The table must render one row per `TestTimings` entry and include these columns:

| Column | Source | Behaviour |
| --- | --- | --- |
| Test name | `testBody.title` | Display the full title path in a readable form. This is the searchable and sortable name. |
| Status | `status` | Show the existing Playwright status in a visually distinct, accessible form. |
| Duration | `totalDuration` | Display a human-readable duration and sort by the underlying numeric milliseconds value. |
| Project | `projectName` | Display when project information is present, so same-named tests can be distinguished. |
| Retry | `retry` | Display when applicable, so individual attempts are recognizable. |
| Shard / merged report | `mergeReportId` | Display when applicable, using the current report terminology. |

The UI may hide context columns that have no meaningful values in a given report, provided it does
not hide the test name, status, or duration columns.

### Search

- Place a visible search input adjacent to or directly above the table.
- Filter as the user types; no submit action is required.
- Match test names case-insensitively using substring matching against the full title path.
- Preserve the active sort when filtering.
- Show an explicit empty state when no rows match.
- Clearing the input restores all rows.

### Sorting

- The Test name and Duration column headers must be interactive sort controls.
- Selecting a sortable header sorts ascending; selecting it again reverses the direction.
- The active column and direction must be perceivable visually and programmatically (for example,
  with `aria-sort`).
- Name sorting is locale-aware/alphabetical and deterministic.
- Duration sorting uses numeric `totalDuration`, not the formatted duration string.
- Define and implement a deterministic secondary sort for equal values (recommended: original data
  order, then test name) so rows do not appear to jump unexpectedly.
- Initial ordering should preserve the report's current input order. No column is sorted until the
  user selects one.

### Failure visibility and accessibility

- Use an outcome treatment that lets users distinguish failed, passed, skipped, timed-out, and any
  other supported Playwright statuses without relying on colour alone.
- Search input, sort headers, and table cells must be usable by keyboard.
- Associate a visible or screen-reader-accessible label with the search input.
- Use semantic table markup (`table`, `thead`, `tbody`, `th`, `td`) and appropriate header scopes.

### Layout and responsiveness

- Add the table as a report-app section without disrupting the current header, summary cards,
  chart, command-palette search, selection, or tooltips.
- Keep the table readable in both existing light and dark themes.
- On narrow viewports, preserve access to all essential columns via a responsive layout or horizontal
  scrolling; do not truncate test identity or remove status/duration.
- The report remains self-contained: no network request or external service is introduced.

## Technical Direction

- Implement the browser UI under `src/report/`, with a dedicated React table component and related
  data/view-model helpers as needed.
- Reuse the existing `TestTimings` model rather than creating a second serialized representation.
- Follow repository rules: a concise top-of-file JSDoc for every new `src/` file, exported
  functions/components before helpers, and separate component files except for tightly coupled
  small components.
- Add table-specific styles through `src/report/css/index.css`; use the existing theme variables.
- Keep the current command-palette search independent; its purpose is chart focus and broader
  report search, whereas this input filters table rows.

## Acceptance Criteria

1. A report containing _N_ `TestTimings` records renders _N_ table rows before filtering,
   including retry records.
2. Each row displays a full test title path, status, and formatted total duration.
3. Entering a case-insensitive partial test title shows only matching rows; clearing it restores the
   full result set.
4. Clicking Test name sorts rows ascending; clicking it again sorts descending.
5. Clicking Duration sorts numeric duration ascending; clicking it again places the longest
   executions first.
6. Search results remain correctly sorted using the active sort order.
7. A report with no search matches displays an explicit empty state.
8. Existing reports generated from unchanged Playwright configurations render successfully; no new
   reporter option or JSON field is required.
9. The table works in light and dark themes and remains usable at a narrow viewport width.
10. Automated coverage verifies row construction, searching, both sort directions for both sortable
    columns, retry handling, empty state, and unchanged report generation/consumption.

## Validation Plan

- Add focused unit tests for row mapping, search, and sort behaviour.
- Add or extend browser-level report tests to confirm visible rows, search interactions, sort
  controls, status rendering, and the empty state against representative generated report data.
- Exercise existing fixtures/configurations that cover a single project, multiple projects, shards,
  and retries where available.
- Run `npm run tsc`, `npm run lint`, and the relevant Playwright test suites. Run `npm run test:all`
  before release when practical.
